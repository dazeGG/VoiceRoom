# План: загружаемые аватарки пользователей и комнат

Статус: план утверждён (обсуждение 2026-07-11), без кода. Реализация — ветка `feature/avatars`,
ПОСЛЕ мержа рефакторинга фолбэка комнат (см. [ROOM_FALLBACK_REFACTOR_PLAN.md](ROOM_FALLBACK_REFACTOR_PLAN.md)).
Цель: загрузка картинок-аватарок для пользователей и комнат; хранение на локальном диске
(S3-ready через абстракцию); акцентный цвет плитки разговора, вычисляемый из аватарки
пользователя; кроп-диалог с живым превью.

## Зафиксированные решения

1. **В БД хранится ключ файла, не URL и не путь.** URL собирается при отдаче наружу.
   Миграция на S3 потом = вторая реализация storage-интерфейса + перенос файлов,
   ноль изменений в БД и протоколе.
2. **Обработка на сервере через sharp**: проверка магических байтов (jpeg/png/webp),
   cover-ресайз 256×256, перекодирование в webp (EXIF/GPS срезается, decompression-бомбы
   отсекаются), лимит входного файла ~5 МБ. Клиент присылает уже кропнутое, но сервер
   всё равно нормализует — клиенту не доверяем.
3. **Отдача через API** (`GET /api/avatars/:key`), Caddyfile не меняется.
   `Cache-Control: public, max-age=31536000, immutable` — ключ содержит хеш, URL иммутабелен,
   смена аватарки = новый ключ (кеш-бастинг бесплатно).
4. **Кроп-диалог на клиенте**: маска по форме использования — circle (пользователь) /
   squircle (комната); экспортируемый bitmap всегда квадратный (форма — визуальный оверлей).
   Справа живые превью: для пользователя — плитка разговора + низ сайдбара, для комнаты —
   карточка лобби. Свой компонент в духе UI-кита, без внешних библиотек.
5. **Акцентный цвет — только у пользователей.** У комнат потребителя нет (карточка показывает
   саму аватарку). Добавить комнатам потом = одна миграция + бэкфилл из хранящихся
   256px-файлов. Вычисляется на сервере один раз при загрузке, хранится в БД.
6. **Загрузка только авторизованным**: свой профиль — любой залогиненный; аватарка комнаты —
   только владелец (по аналогии с модерацией — только статичные комнаты).
   Гости — всегда фолбэк.

## Алгоритм акцентного цвета (Discord-подобный)

1. Сервер: sharp по нормализованной картинке → `stats().dominant` → доминирующий RGB.
2. `deriveAvatarAccent(rgb)` (общая чистая функция в `packages/shared`):
   RGB → OKLCH; **hue сохраняем**, **chroma зажимаем** (~≤0.1), **lightness фиксируем**
   в тёмной полосе ~0.32–0.38 (подобрать под тему hue 112). Фиксированная светлота —
   гарантия читаемости аватарки на фоне. `foreground`/`shadow` выводятся из того же акцента —
   сохраняем контракт `getAvatarPresentation`.
3. Особые случаи: серое/чёрное/белое → нейтральный тёмный; очень тёмная аватарка —
   подстраховка существующими ring/shadow плитки, при необходимости поднять lightness.
4. Клиент использует ту же функцию для живого превью в кроп-диалоге (доминирующий цвет —
   грубая гистограмма по canvas). Источник истины — серверное значение из БД.

## Фазы

### Фаза 1 — Хранилище (API)
- `apps/api/src/lib/avatar-storage.js`: `save(key, buffer)` / `remove(key)` /
  `createReadStream(key)`; реализация — локальный диск поверх `UPLOADS_DIR`
  (новый параметр в `lib/config.js`, дефолт для dev — локальная папка вне git).
- Ключи генерирует только сервер: `av_<userId>_<hash8>.webp`, `room_<roomId>_<hash8>.webp`;
  строгий regex на ключ — path traversal исключён by design.
- **Verify:** юнит-тесты: запись/чтение/удаление, отказ на невалидный ключ (`../`, абсолютный путь).

### Фаза 2 — Миграция БД
- `users.avatar_key text null`, `users.avatar_accent varchar(7) null` (hex),
  `rooms.avatar_key text null`. Down: drop.
- Дополнить `migration-schema.test.js`.
- **Verify:** `db:migrate` + `db:rollback` на тестовой БД, `npm test`.

### Фаза 3 — Акцентная функция (shared)
- `packages/shared`: `deriveAvatarAccent({r,g,b})` → `{ background, foreground, shadow }`
  (см. алгоритм выше). Используется сервером и клиентом.
- **Verify:** юнит-тесты на граничные случаи: серое, чёрное, белое, перенасыщенное,
  очень тёмное; идемпотентность и валидный hex на всём диапазоне.

### Фаза 4 — Эндпоинты (API)
- Зависимости: `@fastify/multipart`, `sharp`. **Рано проверить сборку sharp в
  `node:20-alpine` (musl prebuilt)** — если проблема, узнать о ней в начале, не в конце.
- Общий модуль-конвейер: multipart → лимит размера → magic bytes → sharp (256×256 webp) →
  `stats().dominant` → accent (только users) → `storage.save` → удалить старый файл →
  обновить строку БД. Эндпоинты — тонкие обёртки:
  - `POST /api/auth/avatar` + `DELETE /api/auth/avatar` (авторизованный, свой профиль);
  - `POST /api/rooms/:id/avatar` + `DELETE` (владелец статичной комнаты);
  - `GET /api/avatars/:key`: regex-валидация, stream, `Content-Type: image/webp`,
    immutable-кеш, 404 если нет.
- Rate limit загрузок через существующий `lib/rate-limit.js`.
- `toPublicUser` (user-store): + `avatarUrl`, `avatarAccent`; проекции комнаты: + `avatarUrl`.
  Проверить, что ВСЕ realtime-конверты с пользователями (участники, друзья, ЛС, чат)
  проходят через единую проекцию — иначе поле разъедется.
- При замене/удалении аватарки старый файл удаляется (осиротевших файлов не копим).
- **Verify:** интеграционные тесты Фазы 8 (пишутся вместе с эндпоинтами) + ручной curl.

### Фаза 5 — Deploy
- `docker-compose.yml` + `docker-compose.dev.yml`: named volume `uploads` →
  `/data/uploads` только в api-контейнер; env `UPLOADS_DIR=/data/uploads`.
- Доки: volume `uploads` входит в бэкап наравне с `postgres_data`.
- CSP: для превью кропа через `URL.createObjectURL` добавить `blob:` в `img-src`
  (сейчас `'self' data:`); либо превью через canvas dataURL без правки CSP — решить по месту.
- **Verify:** `docker build` проходит (sharp собрался), компоуз поднимается,
  загрузка + отдача работают на живом стенде.

### Фаза 6 — Web: Avatar и акцент
- `AvatarProps` + `src?: string | null`: есть `src` → `<img>`; нет или `onerror` →
  текущий фолбэк (буква + цвет пользователя / статичный фон комнаты). Битый файл
  не должен ломать UI.
- `getAvatarPresentation` (`client/ui/avatar-presentation.ts`): приоритет
  `avatarAccent` → палитра по `avatarColorKey`.
- Прокинуть `avatarUrl`/`avatarAccent` по типам: `packages/shared`, `client/core/types.ts`,
  модели лобби/друзей/ЛС.
- **Verify:** `check` + `build`; в превью: плитка красится акцентом, битый URL падает в фолбэк.

### Фаза 7 — Web: кроп-диалог
- Компонент по конвенции UI-кита (папка, `types.ts`, scoped-стили), без внешних библиотек:
  файл-пикер → зум + перетаскивание → маска `shape` (circle/squircle) →
  `canvas.toBlob()` → multipart POST.
- Панель превью справа: пользователь — плитка разговора + низ сайдбара (панель профиля);
  комната — карточка лобби. Живой пересчёт акцента: грубая гистограмма canvas →
  `deriveAvatarAccent` (та же функция, что на сервере).
- Интеграция: `SettingsModal` (профиль), `RoomSettingsDialog` (владелец).
- **Verify:** ручная проверка в превью: загрузка, замена, удаление; отражение в плитке,
  сайдбаре, карточке; акцент в превью совпадает с серверным после сохранения.

### Фаза 8 — Тесты (пишутся по ходу, здесь — контрольный список)

## Риски и открытые вопросы

- **sharp — первая нативная зависимость API.** Prebuilt-бинарники для linux-musl есть,
  но проверить Docker-сборку (x64/arm64) в начале Фазы 4, не в конце.
- Не все realtime-проекции пользователей могут идти через `toPublicUser` — ревизия на Фазе 4.
- Очень тёмные аватарки: акцент может сливаться с плиткой — см. алгоритм, п.3.
- Аватарки комнат — только статичные комнаты (у эфемерных нет владельца): подтвердить
  правило по месту, по аналогии с модерацией.
- `api`-контейнер перестаёт быть stateless (volume) — учитывать при будущих сине-зелёных
  деплоях; S3 потом снимает это ограничение.
