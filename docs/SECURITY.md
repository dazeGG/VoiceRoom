# Security

The room access model, accounts and data storage.

Rooms are private only by the link. Anyone who has the room URL or code can enter. The backend issues LiveKit tokens only for existing room sessions, but that does not replace authorization or passwords on the rooms themselves. Chat follows a presence model: reading is allowed by the room link or code, and writing is allowed only for an active room participant with a valid peer session or a signed-in user.

Accounts exist so someone can own persistent rooms, not so they can control access to those rooms. Passwords are hashed with `scrypt` (built-in `node:crypto`). The session lives in an HttpOnly + SameSite=Lax cookie (`vr_session`) until `SESSION_TTL_MS`. Sign-in and registration attempts are limited by `AUTH_RATE_LIMIT` per IP. The login is normalized to lowercase and is unique. When a signed-in user creates a persistent room, it receives an `owner_id`, and the «Мои комнаты» (My rooms) list comes from the server (`GET /api/auth/rooms`). Temporary rooms stay ownerless.

The «Безопасность» (Security) tab shows every active session of the account: the browser or app, the OS, the last visit, and the city and country determined from the IP through the local DB-IP database. The IP address itself is not stored in the session and is not sent anywhere. The last visit is updated at most once an hour. Another session can be ended: its cookie stops working, the WebSocket closes with code `4401`, and that device's voice drops immediately — only that peer's gate credentials are revoked, so the account's other devices stay in the call. Changing the password and recovering access end every session of the account.

Recovery codes are ten one-time codes of 16 Crockford base32 characters (80 bits). Creating a set requires the current password. The codes are shown once, and a new set cancels the old one. The database stores only the SHA-256 of `<user id>:<code>`. Signing in with a code (`POST /api/auth/recover`) sets a new password and is limited by `AUTH_RATE_LIMIT` separately per IP and per login. While the account has no unused codes, a reminder is shown above the rooms in the lobby. The close icon hides it for 3 days on every device (`users.metadata.recoveryCodesReminderSnoozedUntil`).

Every sign-in is recorded in `account_login_events` (device, city, time; kept for 90 days). If the browser, OS and city have not been confirmed in the last 30 days, the account's other devices get a «Новый вход в аккаунт» (New account login) modal: immediately over the WebSocket, as a push notification even in «Не беспокоить» (Do not disturb) mode, and on the next visit if nothing was open. «Это я» (It's me) confirms the device. «Это не я» (It's not me) ends that session at once (cookie, sockets, voice) and offers a password change or a refresh of the recovery codes. An unanswered or rejected sign-in does not make the device familiar. An answer on one device closes the question on all of them, and with no answer it disappears after 14 days.

An account can be deleted on the «Безопасность» (Security) tab after the password is entered. It is hidden at once: every session and socket ends, the name becomes «Удалённый аккаунт» (Deleted account) everywhere, and the account cannot be found, written to or invited. Signing in with the password within 7 days offers to restore the account as it was. When the period ends, the API maintenance timer finishes the deletion: each persistent room passes to the oldest participant who is not being deleted and is not banned in it (a room with no such participant is deleted), and friends, requests, blocks, room membership, notification settings, push, recovery codes and sign-in history are deleted. The user row stays anonymized, so other people's direct messages and room messages do not disappear, and the previous login is stored as a hash in `reserved_logins` and is not registered again.

The «Что нового в VoiceRoom» (What's new in VoiceRoom) modal is shown once per release: the account stores the last announcement version it viewed (`users.metadata.whatsNewSeen`), and new accounts receive the current version immediately. For the next release, raise `WHATS_NEW_VERSION` in `packages/shared/src/account-security.ts` and update the item list in `apps/web/src/features/home/model/whats-new.ts`.

The owner of a persistent room can remove a participant or create a ban. A ban is matched to the participant's account, if they are signed in, and to the IP of the current peer session (the database stores only the address key from `apps/api/src/lib/ip-key.ts`; for IPv6, the key of its /64 network, so a guest ban applies to the whole /64). It is checked on entry, when a LiveKit token is issued, when a message is sent and when a preview subscription is made. Kick/ban invalidates the peer session and removes the participant from LiveKit. This is a moderation tool, not a private-room mode: any user who is not blocked and who has the link or code can still enter.

Web Push is available only to signed-in users and is off without a complete set of VAPID keys. Subscriptions are stored on the server. DND silences push entirely, and muting a DM thread silences push for that conversation only. A room mute is stored in the account's server-side settings, syncs across the account's devices and silences system notifications and sound alerts for that room. Pushes to the Android app go through RuStore Push, and only to signed-in users: the device token is bound to the session and is deleted with it (sign-out, ending the session, a password change, account deletion). DND and mute work the same way as for Web Push. Web Push content is encrypted end to end (RFC 8291), and the browser's push service cannot see it, whereas RuStore delivers the push text to Android in the clear through its servers. The private notification-text setting hides the text in both cases. The sender's or caller's name stays in the title, and the room name is not sent for a call.

Persistent rooms are no longer counted against the IP quota: only authenticated users can create them, and ownership is limited by `MAX_STATIC_ROOMS_PER_USER` (3 by default). Temporary ownerless rooms stay limited per IP by `MAX_TEMP_ROOMS_PER_IP` (the legacy `MAX_EMPTY_ROOMS_PER_IP` is used only as a fallback for old env files), so that one IP cannot fill `MAX_ROOMS` with empty temporary rooms.

Chat history is stored in PostgreSQL indefinitely: messages do not expire and are not trimmed by count, and there is no setting for that. A message disappears only if its author or the owner of the persistent room deleted it, or if the room itself was deleted. After `RETENTION_KEEP_DELETED_MS` that message is erased from the database, its attachments are marked deleted, and media cleanup removes their files. Sending chat is limited by `ROOM_CHAT_RATE_LIMIT` per IP+room pair over `ROOM_CHAT_RATE_WINDOW_MS`. In production, back up the `postgres_data` and `uploads` volumes together, and do not lose `DATABASE_URL` or the credentials. Cleanup of idle dynamic rooms runs on a process-local `ROOM_PRUNE_INTERVAL_MS` timer; old soft-deleted rows are physically purged by `RETENTION_PURGE_INTERVAL_MS` after `RETENTION_KEEP_DELETED_MS`. API currently assumes exactly one running instance: presence (including peer IP for moderation), WebSocket registry, Ring, POW challenges, cleanup timers and non-durable rate-limit state are process-local. Durable rooms/messages/users, bans and push subscriptions live in PostgreSQL, avatar files live on the API `uploads` volume, and room quota/capacity enforcement is transactional in PostgreSQL at room creation time. Horizontal scaling requires sticky WebSocket routing, shared avatar storage such as S3 and moving other process-local state to shared storage such as Redis/pub-sub.

LiveKit takes the mesh load off the browsers: each participant publishes the microphone and the screen once to the SFU, and the other clients subscribe to tracks through LiveKit.

## End-to-end encrypted 1:1 calls

Every 1:1 friend call is end-to-end encrypted, with no setting and no cleartext fallback. The protection covers call media only: voice, camera and screen share, including screen audio. The server still sees the metadata: who called whom, when and for how long, the display names, and the DMs, which stay plaintext on the server. Rooms, Meet and the widget are not end-to-end encrypted.

**Key agreement.** The two main participants of the call room agree a fresh 32-byte media key for each call, over their LiveKit participant attributes (`vr.e2ee`, `packages/call/src/engine/e2ee/key-agreement.ts`).
- The exchange is ZRTP-style. The caller commits to `SHA-256` of its ephemeral X25519 public key, the callee answers with its own, then the caller reveals.
- `HKDF-SHA256` over the X25519 secret and a transcript gives the media key and 24 bits for the safety code. The transcript binds the call id, the agreement id, both page-instance ids and both public keys.
- The server relays the states but cannot derive the key. The private keys are non-extractable WebCrypto keys and are discarded after each agreement, so a later compromise does not expose past calls.
- A reload on either side runs a new agreement at the next LiveKit key index, so a switch causes no audible gap.

**Safety code.** Both sides show 4 emoji from a fixed 64-emoji table behind the lock in the call («Звонок защищён сквозным шифрованием»). Because the caller commits first, a relay that substitutes keys cannot choose matching codes: they match only by chance, 1 in 16.7 million per call. Comparing the code is optional. A call nobody compared is safe from a passive server, not from an active one.

**Media.**
- **Before the key.** LiveKit frame encryption (AES-GCM, frame key from HKDF) is switched on before the room connects. Until the key exists, the SDK drops every outgoing frame, so nothing leaves the device in clear.
- **Only the roster peer.** A call subscribes only to encrypted publications, and it agrees keys only with the participant the API roster seated. Names come from the roster, never from LiveKit.
- **RED.** RED audio redundancy stays on while the peer's receiver takes it, because the SFU cannot strip encrypted RED for a subscriber that does not. A build plugin lets `livekit-client` send RED under E2EE when the app asks for it (`scripts/build/livekit-e2ee-red.ts`).

**Admission.** A call's LiveKit token (`POST /api/call-rings/:callId/livekit-token`) is issued only to a client that declares `e2ee: 1`; any other gets `426 client_outdated`. A client without the key would hear noise, so it must not get into the room at all. Only these tokens may update their own participant attributes (`canUpdateOwnMetadata`).

**Not covered.**
- The Android app does not take part in calls yet.
- The desktop native voice helper is never used for calls; the encrypted browser path plays them.
- A failed agreement shows «Не удалось установить защищённое соединение» and the call stays silent.
