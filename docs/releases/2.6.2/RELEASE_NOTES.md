# VoiceRoom 2.6.2 — логи, по которым видно сбой

Релиз поверх 2.6.1, обратно совместимый. Миграций нет, схема не меняется, откат сводится к подмене тега образа.

Для пользователя не меняется ничего: весь релиз — про то, чтобы жалобу «звонок отвалился» и «микрофон не заработал» можно было проверить, а не гадать.

## Что было не так

- 33 вызова `console.*` в API шли мимо логгера: строки без уровня и контекста, теряющиеся в общем потоке stderr.
- Жалобу нельзя было связать с запросом — сквозного идентификатора не существовало.
- Realtime почти молчал: ни события подключения и отключения, ни кода закрытия сокета — самого диагностичного факта об оборванном звонке.
- Задачи обработки медиа исчерпывали попытки и помечали вложение мёртвым вообще без записи: загрузка, которую ждал пользователь, просто не появлялась.
- 75 вызовов `console.*` во фронте не доходили никуда, так что сбои микрофона, демонстрации экрана и переподключения на чужой машине были не видны совсем.

## Структурные логи

- Один логгер на API, воркеры и LiveKit-гейт: каждая запись — строка JSON с полями `service`, `version`, `env` и кодом события `evt`, по которому строятся поиск и алерты.
- Пароли, токены сессий и восстановления, адреса почты, `authorization` и `cookie` вырезаются при записи на любой глубине вложенности. Адреса клиентов попадают в лог только как посоленный хеш.
- Содержимое сообщений, чат комнат и вложения не логируются.

## Диагностика по идентификатору запроса

- Каждый ответ несёт заголовок `x-request-id`, включая ошибки, о которых сообщают чаще всего. Присланный с фронта идентификатор переиспользуется, если он безопасен для записи, и заменяется, если нет.
- Браузер запоминает этот идентификатор при неудачном вызове API, так что жалоба сводится к одному поиску по логу.
- Realtime связывается по `connId`, фоновые задачи — по `eventId` записи очереди.

## Что теперь видно

- Подключение и отключение сокета с кодом закрытия и временем жизни, отказы по лимиту соединений, отклонённые входы в комнату.
- Отказы впуска в LiveKit с тем же кодом, который получил клиент.
- Исчерпавшие попытки задачи медиа, сбои доставки сообщений и уведомлений, ошибки пула PostgreSQL, длительность обслуживающих задач.

## Логи из браузера

- Клиент держит в памяти последние 100 записей и отправляет их на `/api/client-logs`, только когда что-то действительно сломалось: не запустилась комната или восстановление связи дошло до отказа. Не по таймеру, не чаще раза в 30 секунд.
- Принятые записи попадают в тот же поток логов как `client.report`. **В базу не пишется ничего**: ни таблицы, ни миграции, ни отдельного срока хранения.
- Приём выключен по умолчанию и включается отдельно на каждом хосте. Пока он выключен, маршрут отвечает 404, и браузер перестаёт пытаться.

## Обновление

- Миграций нет.
- Новые переменные окружения, все необязательные: `CLIENT_LOG_INTAKE_ENABLED` (по умолчанию `false`), `CLIENT_LOG_RATE_LIMIT` (`6`), `CLIENT_LOG_RATE_WINDOW_MS` (`60000`).
- `LOG_LEVEL` работает как раньше: `info` в production, иначе молчание. Проверки здоровья по-прежнему не попадают в лог запросов.
- Окно «Что нового» остаётся на 2.6.0: этот релиз его не переписывает.
- Контракт логирования целиком описан в `docs/LOGGING.md`.
