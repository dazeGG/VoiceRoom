## Зафиксированные продуктовые решения (2026-07-10, в силе)

| Вопрос | Решение |
| --- | --- |
| Причина кика/бана | Не указывается. Цель видит только «Вас исключили из комнаты» / «Вы заблокированы в этой комнате» |
| Срок бана | Перманентный. В схеме nullable `expires_at` на будущее, UI таймера нет |
| Разбан | Только undo-тост сразу после бана; API-эндпоинт разбана существует (его дёргает undo). Списка «Заблокированные» нет |
| Идентичность бана | Запись = `user_id` (если есть) + IP на момент бана; при входе проверяются **оба**. VPN-обход гостём — принятое ограничение |
| Скоуп модерации | Только статичные комнаты (временные ownerless по дизайну) |
| Ring | Только изнутри комнаты, только друзьям. Фидбек отправителю минимальный, отказ невидим. Эфемерный (~30 сек), журнала пропущенных нет |
| Push-события | Ring, личные сообщения, заявки в друзья (+принятие). Сообщения комнат и «друг в эфире» — нет |
| Доставка push | Сервер шлёт всегда; service worker подавляет показ при вкладке в фокусе. Push только залогиненным |
| DND | Ручной тумблер (без таймера), серверное состояние, индикатор на аватаре |
| Mute треда ЛС | Серверный (гасит push и звук), unread-бейдж остаётся |
| Mute комнаты | Только звуки на текущем устройстве → localStorage (уже сделано в #43 — сверить семантику) |
| Меншены | Отложены (2.5.0) |

Вне скоупа 2.4.0: меншены, **картинки в чате, реакции и reply** (решение
2026-07-11 — кандидаты 2.5.0; картинки — по конвейеру аватарок, набросок был в

## 3. Модерация: кик и бан

**Миграция:** таблица `room_bans` — **уже в репо**
(`20260710130000_add_room_bans.js`): `id varchar(36) PK`, `room_id` FK → rooms
`ON DELETE CASCADE`, `user_id varchar(36)` nullable FK → users
`ON DELETE CASCADE`, `ip text NOT NULL DEFAULT ''`, `created_at`,
`expires_at timestamptz` nullable (в 2.4.0 не читается), `metadata jsonb`.
Индексы `(room_id, user_id)`, `(room_id, ip)`. Лимит `MAX_ROOM_BANS`
(env, default 100) — при переполнении 409.

**Присутствие:** при join/`handleState` запоминать IP пира в in-memory presence
(`getClientIp` уже есть) — источник IP для бана гостя.

**API (владелец комнаты, cookie-сессия, только статичные комнаты):**
- `POST /api/rooms/:roomId/kick {peerId}` — без записи.
- `POST /api/rooms/:roomId/ban {peerId}` → `{banId}`; запись `user_id`
  (accountUserId пира, если есть) + текущий IP пира; затем кик.
- `DELETE /api/rooms/:roomId/bans/:banId` — undo из тоста.

**Механика кика (общая для кика и бана):**
1. `RoomServiceClient.removeParticipant(livekitRoom, peerId)` из
   `livekit-server-sdk` (для RoomService нужен `http(s)://`-хост из
   `LIVEKIT_URL`). Токен живёт 6 ч — пассивного отказа в токене мало.
2. Инвалидация peer-сессии на сервере (state/token с этим `sessionToken` → 403).
3. Направленное WS-событие `room.kicked {roomId}` / `room.banned {roomId}`
   этому peer-соединению (+ `broadcastToUser`, если залогинен).

**Enforcement бана** (проверка `user_id` ИЛИ IP) на входных точках:
`handleState`, `handleLiveKitToken`, `handleRoomChatPost`, WS-подписка на room
preview. Ответ — 403 с кодом `room_banned`. Попутно перепроверить и закрыть
P2 из аудита: гость может постить в чат произвольной комнаты по ID —
enforcement на тех же входных точках.

**Клиент:**
- `ParticipantContextMenu`: для владельца статичной комнаты — «Исключить» и
  «Заблокировать» (не на себе).
- После бана — тост «N заблокирован» с «Отменить» (~10 сек; дёргает
  `DELETE …/bans/:banId`).
- У цели — полноэкранный экран (по образцу `RoomEntryErrorScreen`), остановка
  реконнектов; те же экраны при 403 `room_banned` на входе.

**Тесты:** права (не-владелец → 403, временная комната → 403), бан гостя по
IP, бан аккаунта (+гостевой вход с того же IP), undo, cap, каскад при удалении
комнаты, инвалидация peer-сессии.

## 4. Web Push (инфраструктура)

**Зависимость API:** `web-push`. **Env:** `VAPID_PUBLIC_KEY`,
`VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`; без ключей push выключен (деградация, не
падение).

**Миграция:** `push_subscriptions`: `id PK`, `user_id` FK `ON DELETE CASCADE`,
`endpoint text UNIQUE`, `p256dh`, `auth`, `created_at`, `last_success_at`,
`metadata jsonb`.

**API:**
- `GET /api/push/config` → `{enabled, vapidPublicKey}`.
- `POST /api/push/subscriptions {subscription}` — upsert по endpoint.
- `DELETE /api/push/subscriptions {endpoint}`.
- `sendPushToUser(userId, payload)`: на все подписки; 404/410 → удалить
  подписку; уважает DND и mute (§6); per-message TTL (для ring).

**Клиент:**
- Service worker `src/service-worker.ts`: `push` → если есть window-клиент в
  фокусе — не показывать, иначе `showNotification`; `notificationclick` →
  фокус вкладки или открытие URL (`/r/<roomId>` для ring, тред для ЛС).
- Подписка + запрос разрешения — только контекстно (тумблер в настройках).
- Payload-типы: `ring`, `dm.message`, `friend.request`, `friend.accepted`.

**Тесты:** CRUD подписок, чистка по 410, нет ключей → `enabled:false`;
отправка мокается (unit на фильтры DND/mute).

## 5. Ring — «Позвать друга»

**API:** `POST /api/rooms/:roomId/ring {userId}` (cookie-сессия):
- отправитель — активный пир комнаты; получатель — друг (`friendships`);
- кулдаун пары: `RING_RATE_LIMIT` / `RING_RATE_WINDOW_MS` (default 1 / 30 сек);
- доставка: `broadcastToUser(userId, {type:'ring.incoming', payload:{fromUser,
  room:{id,name,emoji}, expiresAt}})` + `sendPushToUser` с TTL = `RING_TTL_MS`
  (default 30000);
- ответ отправителю всегда `{ok:true}` — судьба ring невидима.

**Клиент:** кнопка «Позвать» в `RoomTopbar` (только залогиненным): поповер со
списком друзей (онлайн первыми) → тост «Приглашение отправлено». Входящий ring:
глобальный тост «N зовёт вас в комнату X» с «Зайти»/«Отклонить», авто-скрытие
по `expiresAt`; `playRingCue` в `cues.ts` (через sfx-шину, §8). Клик по push —
в `/r/<roomId>`.

**Тесты:** не-друг → 403, не-участник → 403, кулдаун → 429, WS-событие, TTL.

## 6. Настройки уведомлений

Часть §6 уже сделана в #43 (mute по человеку/комнате, громкость сигналов) —
при реализации сверить, что mute треда ЛС серверный (гасит push), а mute
комнаты локальный, и донести недостающее:

**Миграции:** `users` + `dnd boolean NOT NULL DEFAULT false`;
`dm_thread_mutes` (`user_id`, `peer_user_id`, `created_at`,
UNIQUE `(user_id, peer_user_id)`, FK `ON DELETE CASCADE`) — если mute из #43
клиентский.

**API:** `POST /api/notifications/settings {dnd}`; `dnd` в `GET /api/auth/me`;
`sendPushToUser` не шлёт при `dnd` (ring тоже гасится) и при mute треда для
`dm.message`.

**Клиент:** DND-тумблер в меню пользователя + индикатор на аватаре; при DND
глушатся и звуковые сигналы. Вкладка «Уведомления» в `SettingsModal`:
master-тумблер push этого браузера, DND, ссылка на громкость сигналов.

**Тесты:** DND гасит push, mute треда гасит только свой тред, `me`/`dm`
отдают флаги.

## 8. Аудио-шина и мастер-громкость (новое, обсуждение 2026-07-11)

Заменяет двойную схему «`element.volume` до 100% / GainNode выше» единым
WebAudio-графом. Микрофон (capture-цепочка rnnoise → гейт) в шину **не входит**.

**Топология:**

```
Участник N (MediaStream) → MediaStreamSource → gainN (per-user 0–200%) → voiceBus ─┐
Стрим экрана (MediaStream) → MediaStreamSource → streamGain (0–200%)   → mediaBus ─┼→ masterGain (0–200%) → limiter → sink
Осцилляторы уведомлений → cueGain                                      → sfxBus  ──┘
```

- Per-user громкость = индивидуальный гейн; слайдер уведомлений = гейн
  `sfxBus`; мастер — один узел вместо пересинхронизации по всем пирам.
- `DynamicsCompressorNode`-лимитер на мастере — защита от клиппинга при
  стакании 200% × 200%.
- Скрытые `<audio muted>` элементы на каждый remote-трек остаются как
  «активаторы» (квирк Chrome: аудио WebRTC-трека не течёт без прикреплённого
  media-элемента), но звук играет граф через `createMediaStreamSource`.

**Sink-стратегия по возможностям браузера:**
- Chrome/Edge: `masterGain → context.destination` + `AudioContext.setSinkId`.
- Firefox (`HTMLMediaElement.setSinkId` есть, у контекста нет):
  `masterGain → MediaStreamAudioDestinationNode → один скрытый <audio>` +
  `setSinkId` на нём.
- Safari (нет `setSinkId`): прямой `context.destination`, только системное
  устройство (как сейчас). Бонус: буст >100% перестаёт зависеть от способа
  выбора устройства — сегодняшняя «нечестность» слайдера в Safari исчезает.

**Что удаляется:** двойной путь громкости и workaround «one-way street» в
`applyVoiceMediaElementVolume`; `rebuildActiveVoiceAudioElementsForOutputSwitch`
целиком; погоня `unlockAudio()` за каждым элементом (сводится к
`context.resume()` + `play()` sink-элемента в Firefox-ветке);
`getAvailable*VolumeMax`-потолки; дубль `isVoicePlaybackMuted`/`isAppPlaybackMuted`.

**Порядок:**
1. **Спайк AEC (go/no-go до кода):** два клиента, динамики без наушников, весь
   звук через WebAudio — проверить эхоподавление в Chrome/Firefox/Safari
   (исторический риск: AEC не учитывал WebAudio-вывод; сейчас риск уже есть
   для громкости >100%). Если в браузере плохо — для него гибридный fallback
   (голоса через элементы), но сначала проверить.
2. Модуль `audio-bus.ts`: контекст, шины, мастер, лимитер, sink-стратегия,
   unlock.
3. Перевод голосов участников на шину (+ удаление rebuild-логики).
4. Перевод стрима и cues; подключение существующих настроек громкости к
   гейнам шин.
5. UI: слайдер мастер-громкости 0–200% (default 100%) в Настройки → Звук
   (опционально — в док комнаты).
6. Уведомления 0–200%: `MAX_NOTIFICATION_VOLUME` → 200 + кнопка
   «прослушать» (тестовый cue) рядом со слайдером.

**Матрица ручной проверки:** смена устройства вывода на лету, autoplay-unlock,
mute, буст в обе стороны (100→200→50%), эхо без наушников, все три браузера.

## 9. Громкость микрофона (input gain)

Discord-подобный слайдер 0–200% (default 100%) в Настройки → Звук и в доке.

- GainNode в существующую worklet-цепочку микрофона **после** гейта/шумодава
  (усиливаем прошедший голос, не шум), перед публикацией трека.
- `autoGainControl: true` остаётся; слайдер — осознанное смещение поверх AGC
  (простой UX без режимов; отключение AGC — отдельная опция позже, если
  понадобится).
- Лимитер (`DynamicsCompressorNode`) после гейна — защита от клиппинга перед
  Opus при бусте >100%.
- Существующий живой метр микрофона показывает уровень после гейна.
- Персист: `voice-room:mic-volume` (localStorage, по образцу остальных).

## 10. Push-to-talk и настраиваемые хоткеи (веб, в фокусе вкладки)

**Компонент записи клавиши** (новый, `shared/ui`, по структуре UI-кита):
клик по полю → «Нажмите клавиши…» → захват `keydown` (одиночная клавиша или
сочетание с модификаторами), `Esc` — отмена, кнопка сброса к дефолту.
Хранение биндингов в localStorage (`voice-room:hotkey:<action>`), сериализация
в стиле `KeyboardEvent.code` + флаги модификаторов.

**Раздел «Горячие клавиши»** (Настройки → Звук или отдельная вкладка) — три
действия через этот компонент:
- Мьют микрофона — default `Ctrl+Shift+M` / `⌘⇧M`; текущий захардкоженный
  хоткей становится настраиваемым (слушатель room shell читает биндинг).
- Мьют звука (вывода) — новый хоткей, default пустой.
- Клавиша PTT — default пустой (задаётся пользователем при включении режима).

**Режим PTT:**
- Тумблер в Настройки → Звук: «Открытый микрофон» (текущее) / «Push-to-talk».
- В PTT-режиме микрофон замьючен; зажатие клавиши открывает его на время
  удержания + release-hold ~200 мс, чтобы не резать хвосты слов.
- Поверх существующего mute-механизма (не пересоздание трека) — мгновенное
  открытие; индикация в доке.
- Игнорировать срабатывание, когда фокус в текстовом поле (как у хоткея мьюта).
- Ограничение веба: keyboard events приходят только при вкладке в фокусе.
  Глобальный PTT — desktop-shell-проект, вне скоупа. В UI честно пометить
  «работает, пока окно активно».

## 11. Редактирование сообщений

Комната + ЛС единообразно: только свои сообщения, `edited_at timestamptz`,
метка «(изменено)» в ленте, realtime-события `room.chat.edited` /
`dm.message.edited`; линкификация/валидация/лимиты текста — как при отправке.
**Без лимита времени** (решение 2026-07-11) — консистентно с удалением,
которое безлимитно и бесследно; если понадобится вместе с reply в 2.5.0,
добавляется одной серверной проверкой + env без миграций.

Каждый воркстрим — отдельная ветка/PR в `develop` (squash-merge), коммиты по
Conventional Commits, атомарно по сфере (api/web/тесты).
